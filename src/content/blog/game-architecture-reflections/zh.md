我的毕业设计是一款用 Unity 开发的 2D 战术战棋游戏。项目里用了不少设计模式，比如 `Event Bus` 负责模块间通信，`State Machine` 管理交互状态，`Command Queue` 组织命令的执行。

这样设计的最初目的是，我希望让项目井井有条，有良好的可拓展性与可读性。从结果来说，这一目的在一定程度上实现了，但在实际开发中，因为经验不足，有些设计虽然搭起来了，用起来却没有想象中顺手。

项目结束后，我重新看了看这些代码。这里记录两个比较具体的问题，以及如果再做一次，我会考虑怎样调整。

## 通信与流程编排

### 用事件解耦之后，流程变得不好追踪了

战棋游戏里经常需要等待表现层。例如一个回合开始时，要先显示回合提示 UI，等它播放完动画、消失之后，才能继续推进。

目前，我在项目里是用 `Command Queue` 和 `Event Bus` 配合处理这件事：

1. 主流程先放入一个等待表现完成的命令
2. 回合系统发布事件，UI 收到后显示提示
3. UI 播放结束，发布表现完成事件
4. 等待命令收到匹配的事件，完成执行，再调用主流程的下一步

具体实现分布在 [BattleServer](https://github.com/Squad-Quadrant/GraduationProject/blob/master/Assets/Scripts/Systems/BattleFlow/BattleServer.cs)、[AwaitPresentationCommand](https://github.com/Squad-Quadrant/GraduationProject/blob/master/Assets/Scripts/Data/Runtime/Commands/AwaitPresentationCommand.cs) 和 [TurnBannerPresenter](https://github.com/Squad-Quadrant/GraduationProject/blob/master/Assets/Scripts/Presentation/UI/Presenter/TurnBannerPresenter.cs) 中

这套流程可以运作，但是整体比较松散，感觉不太科学，现在来看我对其不太满意。主流程只知道自己在等某一类事件，并不直接知道谁负责完成这件事。UI 那边则需要记得在合适的时候发出通知，而且事件的类别、类型等信息都要与等待条件对应上。

这是一套依赖开发者自己的“约定”运行的系统，哪条路径漏了通知，流程就可能一直停在等待状态。项目里也处理了 UI 打开失败时立即发送完成事件的情况，但每增加一种分支，仍然需要检查这套约定有没有被正确执行。

理解代码时也一样。一个本来有明确先后顺序的过程，被拆成了发布、订阅、回调和命令完成。想看完整流程，需要在几个文件之间来回找。

回头看，这里需要的是一次有明确完成时机的调用。主流程需要 UI 做完一件事，然后继续执行，这种关系完全可以直接表达出来。

现在回头看，我会考虑让 UI 通过接口提供一个可以等待的方法，再用 `async/await` 组织流程。这样至少在阅读主流程时，就能看出哪里显示 UI、哪里等待、哪里继续。取消、异常或 UI 被销毁时如何结束等待，也需要一起设计。比如可以像下面这样使用 `async(UniTask)` 来编排流程：

```c#
// 一个单位的回合就是一个 async 方法，流程一眼可见
async UniTask RunUnitTurn(Unit unit) {
    var intent = await _input.WaitForIntent(unit);   // 等待输入
    var result = _combat.Resolve(unit, intent);      // 瞬时改变系统内部状态
    _bus.Publish(new DamageDealtEvent(result));      // 广播通知
    await _view.PlayAttack(unit, result);            // 等待表现
}
```

事件仍然适合通知其他模块状态发生了变化。但对于这种必须等到结果才能往下走的步骤，事件应该被更谨慎地使用。

### 解耦可以通过接口完成

这里还有一个值得单独说的问题：逻辑层需要调用表现层的能力，并不意味着它必须依赖表现层的具体实现。

比如主流程需要显示回合提示，可以依赖一个 `ITurnBannerView` 接口，由表现层实现这个接口。主流程知道自己需要什么能力，但不需要知道动画怎么播放、UI 对象怎么创建。

这样既保留了直接调用的关系，也可以等待调用完成。相比发布事件后再等另一个事件回来，执行顺序更容易看清楚。

所以，如果只是为了避免引用某个具体类，我会优先考虑接口。没有必要一开始就把调用关系改成事件通信。

### Event Bus 只做真正的广播

对于 `Event Bus`，我想给自己保留一个比较明确的使用原则：**只用它做真正的广播。**

这里的“广播”，指的是发布方只负责通知一件事已经发生，不依赖某个订阅者的返回结果。有没有订阅者、具体有几个订阅者，都不应该决定发布方能不能继续执行。

判断时可以先看两个问题：

1. 发布方是否需要等待处理结果？
2. 接收方是一个明确的执行者，还是可能有零个、一个或多个订阅者？

例如伤害已经结算完成，其他模块可以据此更新血条、记录日志、播放音效。这些响应不需要由伤害计算模块逐个安排，适合通过事件通知。

但“显示一个 UI，等它结束以后再继续”就有明确的执行者和完成时机。即使消息经过了 Event Bus，主流程仍然依赖 UI 的响应。这种情况下，我会优先使用直接调用或可等待的方法。

### Command 要有实际用途

项目中还用了 Command Queue。它提供了一套统一的执行方式，但也需要维护命令对象、完成回调，以及同步和异步命令的不同处理。

对这类流程，我会先看是否真的需要命令队列调度、Undo/Redo 等能力。如果只是想把几个步骤按顺序执行，并等待其中的动画或输入，async 方法可能已经足够。

Command 也可以用于记录操作和回放；重点仍然是项目是否有这些具体需求。[《Game Programming Patterns》的 Command 一章](https://gameprogrammingpatterns.com/command.html)就讨论了这些用途。

所以这次复盘里，我想记下的是：**不要仅仅为了统一执行方式，就把所有操作都包装成 Command。** 如果用不到它提供的能力，还需要手动维护完成通知，就要重新考虑这层封装是否值得。

## 分层与代码组织

### 目前项目的组织方式

目前，项目的代码主要分在 `Core`、`Data`、`Systems` 和 `Presentation` 几个目录下。`Core` 放 Event Bus、状态机和命令队列等基础设施，`Data` 放部分配置、事件和命令，`Systems` 放各个功能系统的实现。Unity 相关的组件，比如继承 `MonoBehaviour` 的对象，大多放在 `Presentation` 中。

这样分类的想法，是把功能逻辑与 Unity 相关代码分开。这一点在目录上有了体现，但同一个功能的代码也因此分散在了不同位置。

比如回合系统的逻辑在 `Systems/Turn`，相关事件在 `Data/Runtime/Events/Turn`，回合提示 UI 又分别放在 `Presentation/UI/Panel` 和 `Presentation/UI/Presenter` 中。理解或修改一个完整功能，需要在这些目录之间来回寻找。Panel 和对应的 Presenter 联系很紧密，也因为代码类型不同而被分开存放。

所以我觉得这次代码组织的内聚性不太好。分类时更多考虑了“这段代码属于哪一类”，对“哪些代码属于同一个功能、经常需要一起修改”考虑得不够。

### 分离纯逻辑和 Unity 相关代码

我仍然认可把纯逻辑和 Unity 相关代码分开的方向。但“方便测试”这个理由，对我来说还不够具体。

更值得关注的是，这样分离以后，实际开发能得到什么：

- **更容易复现问题。** 如果一段逻辑只依赖明确的状态和输入，就可以构造相同条件重现问题，不必每次都把游戏操作到那个状态。随机数、时间等因素也需要一并控制。
- **可以脱离场景运行模拟。** 比如让 AI 执行战斗，观察伤害、掩体、行动点等规则的效果，而不必同时运行所有画面和动画。
- **更容易实现存档、回放和撤销。** 当状态与状态变化比较明确时，记录和恢复它们也更容易处理。

这些收益比单纯说“可测性好”更能说明为什么要拆分代码。当然，分离本身也有成本，需要根据项目实际需要取舍。

我觉得可以把可测性当成检查设计的一种方式：偶尔问问自己，不打开 Unity 场景，能不能给这个服务一些输入，让它独立运行？如果做不到，是确实需要场景里的信息，还是依赖关系没有整理清楚？

### 用 Adapter 连接逻辑和外部系统

如果要让逻辑服务进一步独立，也需要处理它与 Event Bus 的关系。

一种可以尝试的做法是，让服务通过 C# `event` 暴露自身的状态变化，由外部 Adapter 订阅，再转发到 Event Bus。这样，服务本身不必持有全局 Event Bus，原有订阅者也可以继续接收通知。

反过来的方向也一样：如果原来是服务自己订阅全局事件，可以改成 Adapter 订阅事件，再调用服务的方法。

这仍然存在通信关系，但服务需要知道的东西更少了。外部系统怎样传递消息，可以留在外部处理。

同时，我会尽量让数据对象专注于保存状态，由负责修改状态的服务发布相应通知。业务状态变化和后续流程编排也需要分清楚，避免一个数据对象在被修改时顺便推进其他流程。

### 文件夹负责组织，程序集负责约束依赖

这次项目的代码主要分在 `Core`、`Data`、`Systems`、`Presentation` 等目录下。Unity 相关组件大多放在 `Presentation`，逻辑实现放在 `Systems`，不少事件和命令放在 `Data`。

这种分类有一个明显的问题：同一个功能的代码被拆散了。修改回合系统时，需要去找逻辑、事件、UI 和 Presenter；Panel 与对应的 Presenter 也因为类型不同而分开存放。

而且，文件夹本身并不能限制依赖。即使文件放进了 `Systems`，代码仍然可以引用 `Presentation`。目录看起来分层了，实际依赖却未必遵守这套结构。

如果确实需要限制依赖方向，可以用 asmdef 把代码分成不同程序集，只配置允许的引用。对于不应使用 Unity API 的程序集，还可以开启 `No Engine References`，去掉自动加入的 Unity 引用。[Unity 的 asmdef 配置文档](https://docs.unity3d.com/6000.0/Documentation/Manual/class-AssemblyDefinitionImporter.html)说明了这些选项。

这样，一部分规则可以在编译时检查，不用完全依赖开发者记住约定。

### 按上下文、分层、功能组织目录

如果重新组织项目，我会考虑下面这个顺序：

1. **先区分相对独立的部分。** 比如局内战斗和局外菜单、配装，它们可能有不同的生命周期。战斗内部的回合、视野和伤害则联系紧密，不必为了分类继续拆成互不依赖的系统。
2. **再区分各层职责。** `Domain` 放规则与状态，`Application` 编排流程，`Presentation` 处理 Unity 表现与交互。
3. **每层内部按功能聚合。** 回合相关代码放在 `Turn`，单位相关代码放在 `Unit`。事件、命令和配置尽量跟随所属功能，Panel 和对应的 Presenter 也放在一起。

可以先记录一个较完整的参考结构：

```
Assets/Scripts/
├─ Core/                    [asmdef]
│  └─ EventBus、FSM、日志等通用基础设施
├─ Shared/                  [asmdef]
│  └─ 跨模块共享的纯数据与类型
├─ UI/                      [asmdef]
│  └─ 与具体玩法无关的 UI 框架、可复用控件
├─ Battle/
│  ├─ Domain/               [asmdef]
│  │  ├─ Turn/
│  │  ├─ Unit/
│  │  ├─ Combat/
│  │  ├─ Vision/
│  │  └─ Map/
│  ├─ Application/          [asmdef]
│  │  └─ 流程编排、视图接口
│  └─ Presentation/         [asmdef]
│     ├─ Turn/
│     │  └─ Panel、Presenter 等
│     ├─ Unit/
│     └─ Map/
├─ Meta/
│  ├─ Domain/               [asmdef]
│  └─ Presentation/         [asmdef]
├─ App/                     [asmdef]
│  └─ Bootstrapper、LevelLoader、依赖组装
└─ Editor/                  [asmdef]
   └─ 编辑器工具
```

这里的依赖方向也需要一起确定：

- `Domain` 不依赖 `Application` 和 `Presentation`，只引用确实需要的纯数据或基础设施。
- `Application` 依赖 `Domain`，通过接口表达对表现层的需求。
- `Presentation` 实现这些接口，可以依赖 `Application`、`Domain` 和通用 UI。
- `Meta` 和 `Battle` 尽量不直接引用彼此，通过共享类型和外部流程协调。
- `App` 负责把这些部分组装起来。

这个模板是为了记录职责和依赖关系，不需要在项目开始时就把每个目录、每个程序集全部建好。

最小的尝试可以是先独立出 `Battle.Domain`。但它依赖的类型也必须一起整理：自定义程序集不能反过来引用默认程序集中的代码，因此不能只移动一个目录，再继续依赖留在原处的 `Core` 或 `Shared` 类型。[Unity 的程序集说明](https://docs.unity.cn/Manual/ScriptCompilationAssemblyDefinitionFiles.html)

## 其他设计与重构原则

### YAGNI：先有具体需求，再增加抽象

这次复盘里，YAGNI 是一个需要反复提醒自己的原则。

我想把“有没有第二个具体用例”作为增加抽象前的一项检查。如果目前只有一种实现，未来的其他情况也还不明确，就先不急着设计通用框架。

这也需要结合抽象的目的判断。例如前面提到的视图接口，即使只有一个实现，它仍然有一个明确作用：限制主流程对表现实现的依赖。这样的边界，与为了可能出现的新功能提前设计扩展点，理由并不相同。

无论是哪一种，都应该能说清楚当前为什么需要它。否则，接口、基类和中间层会增加代码量，也会增加理解一个功能时需要经过的步骤。

### 遇到问题时，先检查依赖关系

流程难追踪、问题难复现、同一个功能的文件到处都是，这些现象都值得回头检查：模块之间的职责和依赖是否清楚？

比如一个等待命令越来越复杂，需要识别更多事件、增加更多完成条件，就应该重新看看，这段流程是否适合继续用事件编排。

局部问题仍然需要修，但我希望自己以后能多检查一步：新增的处理是在补一个遗漏的情况，还是在维持一套已经很难理解的关系？

这些改法大部分还没有在原项目中实践。先把判断依据记录下来，之后再做类似项目时，也方便对照实际结果继续调整。
